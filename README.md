What I Learned
Project structure matters as much as the code itself. Early on, my test file wasn’t being detected at all  not because the code was wrong, but because I’d placed partN_mini_project.cy.js directly inside the cypress folder instead of inside cypress/e2e/. Cypress is strict about its folder conventions: it only looks for spec files in cypress/e2e by default. This taught me that the test won’t run isn’t always a code problem  sometimes it’s a file-location problem, and the Cypress UI itself (the Create your first spec screen) was actually telling me exactly that.
Cypress’s retry-ability has limits, and timing issues are real. My registration test failed with expected '.../register' to include '/login' — the redirect simply hadn’t happened yet by the time the assertion ran. Cypress does retry assertions automatically, but only up to a timeout (4 seconds by default). I learned that when a page is slower than expected, the fix isn’t to add a blind cy.wait(5000), but to extend the timeout on the specific assertion that needs it (cy.url({ timeout: 10000 })), so the test waits exactly as long as necessary without guessing.
Not every test failure is your fault. The file upload test failed with TypeError: Assignment to constant variable — but that error came from the website’s own JavaScript, not from my test code. Cypress automatically fails a test if the page under test throws any uncaught JS error, even one totally unrelated to what I’m testing. This was an important realization: automated tests run inside the real browser environment, so they’re exposed to bugs in the application itself. The fix — cy.on("uncaught:exception", () => false) taught me that Cypress gives you a deliberate escape hatch for exactly this situation, where you need to test functionality despite a known, unrelated bug elsewhere on the page.
Reading the error panel properly is its own skill. At first the error screen looked overwhelming — full of unrelated analytics network requests (Google Analytics, ad pings) mixed in with the actual failure. I learned to ignore the noise and look specifically for the red/orange highlighted box (AssertionError or TypeError), the file-and-line reference (e.g. partN_mini_project.cy.js:24:14), and the plain-English message above the stack trace — that’s where the real answer always was.
Overall, the biggest lesson wasn’t a specific Cypress command — it was that automated testing is as much about diagnosing why something failed as it is about writing the test in the first place, and that real websites (even “practice” ones) have real bugs and real timing quirks that your tests have to account for.



Reflection
The easiest concept to understand was the basic command set — cy.visit(), .type(), .click(), .check(), .select() — because each command maps almost one-to-one onto an action a real user would take, and the syntax reads like plain English.
Locators and the should()/expect() distinction were similarly intuitive once I saw that should() simply gets retried while expect() doesn’t; writing the same assertion both ways side by side made the difference click immediately.
The most challenging part was waiting and retry-ability, specifically understanding why cy.wait(5000) is discouraged when, on the surface, it “works.” It took experimenting with cy.intercept() and aliased requests to really see that Cypress’s built-in retry-ability already solves most timing problems, and that fixed waits are a workaround for not trusting that mechanism.
Browser interactions (new tabs, native alerts/prompts) were also tricky, since Cypress deliberately doesn’t support multiple tabs the way a human browsing session would, and I had to research the recommended workarounds (stripping target="_blank", using cy.on('window:confirm')) rather than finding an obvious built-in command.
Overall, building tests against a real practice site made the abstract concepts concrete ,seeing a test fail because a selector was wrong, then fixing it and watching the Test Runner go green, was much more useful than reading documentation alone. The biggest lesson was that good Cypress tests are less about memorizing commands and more about asserting on the right condition at the right time.
